User journey: what each step means

1. Choose and version the goal

Input: goal kind, title, desired outcome, criteria and unanswered questions. A criterion records its field, terms, required/preferred importance, contact/opportunity scope and user/suggested origin. Decision: is the criterion actually known? Career aspirations are not self qualifications, and an unanswered fundraising stage is not a seed-stage filter. Output: a selected goal snapshot, local edits and explicit account-save versions. Concurrent account versions require resolution; device-to-account copying requires review and preserves destination ownership.

2. Bring chosen context

Built inputs: a LinkedIn ZIP, résumé PDF, optional existing mbox, manual relationship details and recorded interactions. Files are processed in the browser before account saving. A first conversation can begin with a goal and manual facts; no Takeout archive is required. Gmail, Contacts, Calendar, event integrations and card OCR are planned inputs, not working connections. The user decides which account receives explicitly copied device work.

3. Retrieve before judging

Input: the owned network and query. The existing lexical search finds words across imported records; with a structured goal, the shared assessor ranks that retrieved set, or all records when the query is empty. It never needs to upload all 19,521 imported connections to rank locally. The UI retains up to 500 actual matching candidates and shows five per page. No match is a useful result: change the criterion or add evidence. An optional web button is a distinct path, not a silent fallback.

4. Save a relationship and inspect its history

Input: a selected network record, manual person or reviewed extension snapshot. Canonical profile URLs support deduplication; a similar name alone does not establish identity. Output: one relationship record, separate goal associations, source context and events. A web result retains its search origin and incomplete status. Saving is not a declaration of fit, a profile read or a conversation. A failed list refresh after a confirmed write offers a read refresh, not another unqualified insert.

5. Prepare one grounded conversation

Input: one goal/version, one person, channel, user-stated purpose/request and optionally up to two candidate plus two self facts. Each selected fact must be an eligible original claim of at most 500 characters. Writing samples, raw web snippets and generated knowledge are not automatically promoted to factual message claims. Local output: a deterministic editable draft with selected quotations, citations, explicit unknowns and an evidence fingerprint. No selected background facts is permitted; the wording stays honest about that lack of personalization.

6. Keep save, copy and sent distinct

Save draft: persists the reviewed text for that relationship, goal/version and evidence selection. Copy: writes to the clipboard only. Record sent: creates a goal-linked contacted event only after the user says they sent the message themselves. Edits, a copied message and a provider response are not evidence of sending. A draft keeps its original goal version; changing the goal or selected facts marks the editor context as changed instead of rewriting history.

7. Remember the next step

Input: an explicit note, interaction or next-step description, with an optional follow-up day and related sent event. Output: goal-linked context and due work in Today/Relationships. The user can record progress and stage changes. A connection acceptance, reply and meaningful progress are different events. Automatic reply detection, inbox observation, inferred sentiment and automatic pipeline movement are not current consequences of a save or copy.

8. Resume without losing ownership

The shell has Today, Explore, Relationships and Me; a saved person opens detailed context and composition. Local editor recovery is scoped to account, relationship and goal. Failed requests preserve the attempted snapshot and later edits. Changing accounts invalidates stale responses, and pending extension saves retain their original owner. A fresh device loads saved account goals and processed source facts; it cannot recover data that existed only on another browser.

“Discarded” means excluded from Mighty’s retained parsed output and upload path. It does not erase the user’s original download from their filesystem or promise that every byte disappears instantly from browser memory. Storage is a choice, not a side effect of import

The local workspace uses device or account-specific keys. Save to account writes protected Supabase records after session verification; RLS and ownership constraints isolate users. The private archive bucket stores the sanitized rebuild bundle. Goals, immutable versions, relationship context, drafts, AI cache and usage ledger are distinct record families. Bulk source saving is retryable and spans several operations, so a partial failure is not described as an all-or-nothing transaction.

Fingerprints identify which work is reusable

Source content fingerprints distinguish processed inputs. Knowledge synthesis checks its fingerprint before generating again. A draft fingerprint pins the goal snapshot, person, selected evidence and compiled wording. The assessment’s lightweight evidence key changes with goal content/version, candidate claims and self evidence; it is not a security signature or a persisted trained score. The gateway cache additionally includes account, feature/configuration and prepared request inputs. Editing a relevant input must not reuse a result from another goal, source version or account.

The extension has its own trust boundary

On a verified short-lived handoff, the worker reads the current owner’s saved goals under RLS and requires an exact complete result. The popup assesses each active saved goal using the same application code, without model calls or imported self facts. Device-only and unsaved goal edits stay out. Explicit profile reads preserve visible anchors; search snippets remain unread and unscored. Current role/company promotion requires narrow semantic labels plus visible current-date provenance. Generic headline and experience prose remain context. Native LinkedIn layout coverage is still unverified.

Save retains a stable account-bound operation ID. Worker reload, expiry, replacement handoff and a stale in-flight response cannot move the previous account’s goal context into the new account. No planned message-observation feature is being enabled by this chapter.

Source deletion is a separate end-to-end workflow

Normal editing preserves original evidence and adds corrections or newer context. That does not justify keeping it after an authorized deletion request. Full source deletion must remove or recompute affected claims, summaries, embeddings if introduced, assessments, cached briefs, draft references and eligible feedback derivatives, while preventing pending jobs from recreating deleted material. This complete dependency-aware deletion workflow and backup-expiry UX remain production work; the current map does not claim a finished one-click erasure system.

Typed evidence: what the engine may actually know

An evidence claim carries a subject, field, text, source label/reference, observation time when available, source kind, confidence label and contact/opportunity scope. “Observed” describes where a fact came from; it is not independent verification. Imported company/title fields may support those exact historical record facts. A headline such as “Exploring CEO roles” is context, not proof that the person is a CEO. A company name does not establish FMCG membership. A contact’s city does not establish the location of an available role.

For the narrow current-experience extension path, typed role/company anchors retain the full original entry and separate current date as companions. Past, missing, contradictory, hidden or over-limit fields fail closed. Saved-person evidence uses a qualifying newer current read to label older saved role/company text as previously saved context; raw history is retained. Multiple current entries remain separate and nonexclusive. User-confirmed manual facts remain an explicit path for meaningful information that the parser cannot establish.

Gateway decisions before dispatch

Validate the signed-in account, request shape, feature row and current tariff. Tool input is checked before quota claim. A matching account cache can return a stored answer; a miss must pass active-account/provider-data-control gates and atomically reserve the bounded cost. The reservation returns a frozen configuration used for the actual call, preventing a concurrent model/rate edit from changing its accounting. Provider secrets stay server-side. A parent request reserves first when it invokes a separately metered child tool.

Charge accounting after dispatch

Confirm reported input, output and cache-related token usage against the frozen tariffs. A cache hit records zero new provider usage; the earlier generation still had a cost. A definitive rejection or failure before dispatch releases the reservation. An uncertain provider outcome or pending confirmation retains it for reconciliation and must not trigger an automatic paid retry. A generated but unusable response can still be metered. Search’s configured fixed tariff is a planning/accounting charge, not invoice-confirmed treatment of a shared free allowance.

Validation is specific to the output

The classifier must return a recognized route. Knowledge synthesis validates its schema and cited evidence. The optional conversation recipe may reorder only the exact chosen claims, preserve the user’s purpose/request and select fixed greeting/closing choices; unknown IDs, altered quotations or unchecked prose fail validation. User editing happens after compilation and remains user-authored text. Prompt instructions alone do not make Ask or web output perfectly factual; show limitations and retain source review.

Future intelligence needs a new acceptance gate

Bounded grounded research could retrieve public sources, validate identity, retain factual “why retrieved” lines and then assess sufficient evidence. It is not a complete LinkedIn read. Direct Gmail and notification-body analysis need separate scope, retention and event-validation design. Learned ranking requires consent-compatible judgments, held-out tests, source restrictions and measured advantage over this baseline. No reply is not a negative fit label; saves and copies are not successful outcomes. Permission for inference does not authorize general-model or cross-account training.

Review the map before extending it

  1. Core loop: demonstrate one goal, evidence, relevant contact, editable local draft and explicitly recorded next step without Gmail or a paid model dependency.
  2. Parity and recovery: verify source preservation across import, extension inbox and saved-person assessment; verify account switches, goal-version changes, stale responses and unfinished draft recovery.
  3. AI: verify each enabled feature independently with bounded input/output, strict applicable validation, cache isolation, real usage confirmation and failure reconciliation.
  4. New connectors: agree the exact visible information and authorized body access first; test coverage and ambiguous identity without turning weak signals into automatic stage changes.
  5. Learning: evaluate retrieval and evidence quality separately, then compare a proposed ranker against the fixed baseline. No new training pipeline is implied by recording ordinary relationship activity.

Product direction · For review

A useful next conversation, supported by evidence

Mighty should help Ritesh decide whom to contact, understand why that person matters to a particular goal, make an appropriate request, and follow through. Its promise is a better next action. A larger contact database, a longer personal profile, or more generated messages does not establish that value.

Start with a specific professional goal

The recommended first workflow supports a Chief AI Officer role in FMCG, focused on New York, Chicago, San Francisco, and Boston. Confirm timing, acceptable company types, location flexibility, demonstrated business outcomes, and the conversation Ritesh wants now. Adjacent titles such as Head of AI are a proposed expansion, not an automatic replacement of the goal.

A useful contact might be a hiring decision-maker, an executive-search partner, an industry operator, or a trusted introducer. These people help differently. The second goal is fundraising for Mighty; stage, target amount, traction, and investor profile remain unknown. MIT affiliation and Boston proximity may support a connection reason, but neither establishes investment fit.

The cofounder challenge

The hypothesis is that useful relationships remain inactive because people cannot confidently choose their next conversation. Sometimes the missing ingredient is a clear request, evidence of value, or willingness to reconnect. More research will not solve every one of those problems.

“No one has done this” is not a defensible pitch. Competitors already advertise substantial overlap:

  • Affinity combines captured activity, relationship intelligence, introduction paths, and agents that produce briefs and follow-ups.
  • Dex offers LinkedIn synchronization, relationship memory, browser integration, and AI access to contacts, notes, and follow-ups.
  • folk’s Follow-up Assistant identifies inactive conversations with pending actions and proposes messages using conversation history and the user’s voice.
  • LinkedIn Sales Navigator offers lead summaries, shared-connection paths, and personalized Message Assist outreach.

These are vendors’ descriptions, not independent demonstrations of quality. Mighty’s proposed distinction is an inspectable workflow for an individual’s specific goal: evidence, an appropriate ask, a real action, and a remembered outcome. Demonstrate that experience before claiming superiority.

Primary-source research · 12 September 2026

Win a specific relationship decision

The category is occupied. Mighty needs to prove that its complete experience helps an individual choose and pursue a useful conversation. Network search, relationship memory, extensions, and personalized messages are insufficient differentiation individually. Professional goals define the market; the cohort is the first route in

Mighty is for people pursuing concrete professional goals: career moves, fundraising, and building teams. The founder’s MIT, student, and cohort network is the initial go-to-market channel for reaching prospective users and learning quickly. The product’s positioning follows those professional goals across career stages. Campus or MBA membership does not define the addressable customer.

Retrieval and explainable goal fit

Retrieve broadly, establish facts narrowly

  1. Compile intent. Turn the confirmed goal and query into target-contact roles, terms, constraints, and unresolved fields. Cache by goal version and query. Classification failure must leave local results available.
  2. Search the owned network first. Build a field-aware lexical index over company, role, and observed profile facts. Add reviewed aliases such as FMCG and fast-moving consumer goods. Do not classify every consumer company as FMCG.
  3. Test semantic retrieval. Embeddings may recover differently worded responsibilities, but produce candidates for verification rather than established qualifications. Select processing location and storage explicitly; imports must not silently acquire a new data destination.
  4. Merge and deduplicate. Use canonical LinkedIn URLs for identity; uncertain name matches need review. Compare reciprocal rank fusion with lexical retrieval rather than mixing incompatible raw similarity scores.
  5. Expand explicitly. Search public profile URLs behind the web button; snippets remain unscored. Automated LinkedIn capture remains a separately gated prototype, subject to the platform-permission review; it is not required for the core workflow. Offer bounded research with identity checks and citations.
  6. Assess and draft. Extract criterion evidence and unknowns. Compose from those findings, relevant self proof points, relationship history, and the user's writing samples.

For an RRF experiment, use RRF(d) = Σ 1 / (k + rank_j(d)) over retrieval lists containing candidate d. Tune the constant and retrieval window on development queries. The result orders retrieval candidates; it is neither fit nor confidence. See Elastic's official RRF reference. This algorithm does not require adopting Elasticsearch.

Calculate fit without hiding uncertainty

For each confirmed criterion, return supported, contradicted, unknown, or conflicting, with evidence IDs. Conflicting evidence stays unresolved. Required criteria apply to the intended contact role: a recruiter and a hiring leader have different contracts. Sharing the desired job title does not automatically make someone helpful.

Let weights sum to one. Define L = Σ supported weights, U = L + Σ unresolved weights, and C = Σ resolved weights. The interval [L, U] represents established support and remaining possibility; C measures coverage. These are internal decision aids, not probabilities or measures of a person's worth.

Group results by required criteria supported, still unresolved, or contradicted. Within groups, order by supported weight, material evidence freshness, and retrieval relevance. One known criterion must not create apparently perfect fit. Display supported reasons, missing requirements, and source dates. Keep relationship context separate. Preserve the exact authoritative company-overlap statement without turning it into a mutual-connection claim.

An LLM may propose interpretations and evidence links. Deterministic checks enforce known identity identifiers, source references, and quotation/date consistency. Ambiguous identity and semantic support require corroboration or review; a valid citation alone does not prove its claim. Number matching cannot validate an achievement without matching context. Unsupported interpretations remain reviewable suggestions. Use descriptive coverage labels until calibration supports stronger language.

What the current ranking number actually means

Algorithm: weighted additive scoring with eligibility filtering. For each supported criterion, the internal ordering weight adds 10 for a user-required condition, 6 for a user-preferred condition, or 2 for a suggested condition. Career contact routes add 8 for a target-role peer, 4 for a recruiter, 3 for an executive contact and 2 for a shared-employer introduction route; a shared employer adds another 1. Each contradicted criterion subtracts 8 and each conflicting criterion subtracts 4. These hand-set weights are an inspectable baseline, not learned preferences.

rank = supported criterion weights + evidenced contact-route weights
       + shared-employer weight − contradiction penalties − conflict penalties

eligible = at least one supported criterion or possible contact route
           and no user-required contradiction, unless explicitly included

Unknown criteria contribute no support and remain visible as unknowns. That is different from asserting failure, although sparse evidence can still reduce ordering weight. A candidate may be returned with a conflict requiring review; the formula does not implement a universal hard-conflict exclusion. Ties use name and stable key for reproducible ordering. No percentage, hiring authority, vacancy, willingness to help or expected reply is inferred. The support interval proposed in the scoring chapter is a future design; it is not this current implementation.

Broader role equivalence, industry taxonomies, numeric check-size ranges, chronology and opportunity eligibility need explicit extraction and validation before they influence ranking. Current token rules cannot compare investment amounts or prove that an executive is hiring. A useful upgrade must improve recall without turning unknowns into asserted qualifications.

The present AI draft recipe has few degrees of freedom. A larger writing model may add cost without improving that restricted task. Benchmark the local compiler first; expand generation only when evidence-grounding checks and human review demonstrate a useful gain.
